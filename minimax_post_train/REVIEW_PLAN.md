# Review Plan: Top-k Negamax Post-Training

This plan splits the review into focused stages so each pass has a narrow scope and clear deliverables. Each stage should end with concrete findings and action items.

## Stage 1: Spec-to-Implementation Parity
**Goal**: Verify that the implementation aligns with `POST_TRAIN_SPEC.md` and explicitly track any intentional deviations.

**Scope**
- Candidate generation rules (root vs internal nodes, top-k + random neighbor).
- Negamax depth/branching, leaf evaluation perspective, terminal handling.
- Q-based sampling (top-5 only, normalization, temperature).
- Loss definitions (ranking-inside, separation-outside, value target).
- Progressive unfreezing schedule (N, M, order).
- Logged metrics and CSV schema.

**Deliverables**
- A parity checklist with “matches / differs / missing” for each spec item.
- A list of deviations with rationale (if any), and risk assessment.

---

## Stage 2: Data Flow and Sample Integrity
**Goal**: Ensure data generated by search is correctly recorded, transformed, and consumed by training.

**Scope**
- `SearchSample` fields and consistency (obs, candidates, Q values, masks).
- 8-fold augmentation correctness (including candidate/action transforms).
- Q normalization and margin computation stability (edge cases like equal Q).
- Legal mask handling and non-candidate separation set integrity.

**Deliverables**
- Trace of one sample from search → augmentation → loss inputs.
- Edge-case checklist and suggested safeguards.

---

## Stage 3: Search Correctness and Performance
**Goal**: Validate negamax implementation logic and batching behavior.

**Scope**
- Batch tree expansion correctness (leaf generation count, parent-child mapping).
- Negamax backup sign logic and player perspective consistency.
- Root vs internal candidate sizes (6 vs 5) and top-k selection.
- Efficiency considerations: batched eval, memory sizing, device transfers.

**Deliverables**
- A correctness proof sketch for the batched negamax flow.
- Performance risks (OOM, excessive CPU↔GPU traffic) with mitigations.

---

## Stage 4: Losses and Metrics
**Goal**: Confirm losses are implemented as intended and metrics match definitions.

**Scope**
- Ranking-inside loss and dynamic margin logic.
- Separation-outside loss (mean over non-candidates, reference to c4).
- Value loss target (`max Q_search`) and value perspective.
- Metrics (top-1/top-3 accuracy, value MSE) definitions and correctness.

**Deliverables**
- Loss formula vs code mapping.
- Metrics definitions and any detected mismatches.

---

## Stage 5: Training Schedule and Optimization
**Goal**: Verify progressive unfreezing and optimizer management are correct and stable.

**Scope**
- Freeze/unfreeze boundaries (heads → blocks → stem).
- Update intervals (N and M) and block ordering.
- Optimizer recreation logic and parameter coverage.
- Resume/continuity behavior with `training_state.json`.

**Deliverables**
- Schedule table vs code validation.
- Resume safety checklist (optimizer state, unfrozen blocks, counters).

---

## Stage 6: Integration and Runtime Safety
**Goal**: Ensure the main loop, logging, and runtime interfaces are coherent and safe.

**Scope**
- `main.py` integration for search self-play and training loop.
- CSV logging outputs and column consistency.
- Compatibility with existing checkpoints and opponent pool management.
- Device placement, determinism, and error handling.

**Deliverables**
- Integration map (which functions are called, where data flows).
- Logging schema validation and runtime failure risks.

---

## Stage 7: Verification & Minimal Test Plan
**Goal**: Define the smallest practical validation to catch regressions.

**Scope**
- Static checks: imports, `py_compile`.
- Smoke run: short search-based self-play + train.
- Deterministic checks: single position search reproducibility.
- Metric sanity: expected ranges for losses and accuracies.

**Deliverables**
- A minimal executable test checklist with expected outcomes.

---

## Stage 8: Documentation and Handoff
**Goal**: Ensure the final system is understandable and reproducible.

**Scope**
- Update notes on deviations (if any) and rationale.
- Usage guide alignment with new pipeline.
- Known limitations and future follow-ups.

**Deliverables**
- Short addendum to `IMPLEMENTATION_NOTES.md` if needed.
- Final summary of review outcomes.
